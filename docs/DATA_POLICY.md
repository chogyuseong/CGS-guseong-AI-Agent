# 데이터 보관·삭제 정책

이 문서는 BUILD_SPEC 5.1~5.5의 요구를 따른다(5단계 보강, 2026-11-17). 무엇을 어디에 얼마나 두고, 사용자가 지우면 어디까지
지워지는지 저장소마다 적는다. "삭제"를 "모든 저장소에서 즉시 완전 삭제"라고 설명하지 않는다.

설정 값: `EXECUTION_RETENTION_DAYS`(기본 7), `RECEIPT_RETENTION_DAYS`(기본 90). 정리는 1분 검사가 매시 17분에 한다
(`app/automation/retention.py`, 한 번에 200건까지라 많이 밀려 있으면 몇 시간에 걸쳐 끝난다).

## 저장소별 보관과 삭제

| 데이터 | 저장 위치 | 보관 | 사용자가 지우면 | 자동 정리 |
| --- | --- | --- | --- | --- |
| 대화 메시지(내가 보낸 말, 화면에 보인 답) | `messages` | 대화를 지울 때까지 | 대화 삭제로 즉시 지움 | 없음 |
| 모델 기록(모델에 보낸 메시지·응답·도구 호출) | `tasks.message_history` | 끝난 뒤 7일 | 대화 삭제로 즉시 지움 | 7일 뒤 비움 |
| 단계 입력·출력(도구 인자·결과) | `steps.input`, `steps.output` | 끝난 뒤 7일. 메일 결과는 처음부터 앞 500자만 | 대화 삭제로 즉시 지움 | 7일 뒤 `{}`·null. 단계 이름·상태는 남음 |
| 실행 계획 인자 | `action_plans.canonical_args` | 끝난 뒤 7일 | 대화 삭제로 즉시 지움 | 7일 뒤 `{}`(해시는 중복 방지용으로 남음) |
| 승인 카드 문장 | `action_plans.preview`, `approvals.summary` | 대화를 지울 때까지 | 대화 삭제로 즉시 지움 | 없음(작업 기록 화면에 보이는 문장) |
| 실행 영수증(외부 결과 id, 요약) | `execution_receipts` | 90일 | 대화 삭제로 즉시 지움 | 90일 뒤 지움 |
| 내구성 실행 기록(워크플로 입력에 내 메시지, 단계 결과에 모델 응답) | PostgreSQL `dbos` 스키마 | 끝난 뒤 7일 | 대화 삭제 직후 지움(실패하면 7일 정리가 다시 지움) | 완료 7일 뒤 지움. 끝나지 않은 작업의 기록은 남김 |
| 시작 요청 | `outbox_events` | 처리 뒤 7일 | 대화 삭제로 즉시 지움 | 처리한 것은 7일 뒤 지움 |
| 기억 | `memories`(내용, 근거 인용) | 내가 지울 때까지 | 기억 화면에서 즉시 지움. 대화를 지워도 기억은 남음(출처 링크만 끊김) | 없음 |
| 비용 기록 | `usage_logs`(모델 이름, 토큰 수, 비용. 내용 없음) | 계속 | 대화를 지워도 남음(작업 연결만 끊김) | 없음 |
| Google 토큰 | `connections.encrypted_token`(Fernet 암호화) | 연결 해제할 때까지 | 연결 해제로 즉시 지움 | 없음 |

| 테스트 데이터 | `tests/fixtures` | 저장소 | — | 공개 검색 결과의 실제 응답과 문서 형식으로 만든 응답. 키·토큰·개인정보 없음(tests/fixtures/README.md) |

### 남는 것과 한계(숨기지 않는다)
- **기억을 지워도** 예전 대화에 같은 내용이 남아 있으면 그 대화를 이어갈 때 참고될 수 있다. 완전히 없애려면 그 대화도 지운다.
- **대화를 지워도** 이미 바꾼 캘린더 일정 같은 외부 결과는 그 서비스에 남는다. 이 대화에서 만든 기억도 남는다.
- **같은 대화를 계속 이어가면** 가장 최근 작업의 모델 기록에 앞선 내용이 이어져 있다. 7일 정리는 끝난 지 7일이 지난 작업만 본다.
- **끝나지 않은 작업**(대기·실행·승인 대기·취소 요청·재조회)이 있는 대화는 지울 수 없다(409). 실행 중인 기록을 지우면 복구가 망가진다.
- **결과를 모르는 외부 작업**(approved·executing·unknown)이 있는 작업은 재조회에 인자가 필요해 7일 정리에서 빠진다.
- 메일 실행 기록은 500자로 자르지만 암호화하지 않는다(BUILD_SPEC의 `PAYLOAD_ENCRYPTION_KEY`는 아직 없다, 7단계 보강 목록).
- 계정 삭제 화면·API는 없다. DB에서 사용자 행을 지우면 연쇄 삭제되지만 `dbos` 스키마의 기록은 7일 정리를 기다린다.

## 백업과 삭제 지연
- 지금(로컬 개발): 자동 백업이 없다. 데이터는 Docker 볼륨 `postgres-data`에만 있다. 볼륨을 지우면 복구할 수 없다.
- 배포 목표: 백업은 **30일 보관**(BUILD_SPEC 5.2). 백업 안의 데이터는 따로 지우지 않으므로 **지운 대화·기억은 백업에서
  최대 30일 동안 남을 수 있다.** 백업에서 복원하면 지운 데이터가 되살아나므로, 복원 뒤에는 보관 기간 정리를 바로 한 번 돌리고
  복원 시점 이후의 삭제 요청을 다시 적용한다. 실제 배포 서비스의 백업 기능에 맞춰 이 절을 고친다(docs/DEPLOY-OPTIONS.md).
- `dbos` 스키마도 같은 DB에 있으므로 같은 백업에 들어간다.

## 키 관리
| 키 | 쓰는 곳 | 바꾸거나 잃어버리면 |
| --- | --- | --- |
| `TOKEN_ENCRYPTION_KEY` | Google 토큰 암호화(Fernet), OAuth 시작 정보 | 저장된 토큰을 풀 수 없다. 교체 기능은 없다. 키를 바꾼 뒤 사용자가 Google을 다시 연결한다(옛 연결은 해제). 키는 DB와 분리된 `.env`·배포 비밀 설정에만 둔다 |
| `SESSION_SECRET` | 로그인 쿠키 서명 | 모두 로그아웃된다. 유출이 의심되면 바꾼다 |
| `VAPID_PRIVATE_KEY` | 웹 푸시 | 기기마다 알림을 다시 켠다 |
| `ANTHROPIC_API_KEY` 등 외부 키 | 요청 헤더 | 콘솔에서 새 키를 만들고 `.env`를 바꾼 뒤 서버를 다시 켠다 |

키는 `.env`와 배포 비밀 설정에만 둔다. 화면·로그·문서·커밋에 값을 쓰지 않는다(절대 원칙 15).
