# 설계 결정 기록

면접 준비용. 결정과 이유를 날짜와 함께 한 줄씩 쌓는다.

## 0단계: 뼈대

- 2026-11-16 · 에이전트 루프를 프레임워크 없이 직접 구현한다 → 승인 게이트와 기록을 루프 안에 코드로 끼워 넣어야 하고, 면접에서 한 줄씩 설명할 수 있어야 해서.
- 2026-11-16 · Django 5.2 LTS로 고정한다(6.x 아님) → 명세가 5.x이고, LTS라 보안 업데이트 기간이 길다.
- 2026-11-16 · DB는 `DATABASE_URL` 하나로 SQLite/PostgreSQL을 바꾼다. 값이 비어 있으면 SQLite → 개발은 설치 없이 바로, 배포는 환경변수만 바꾸면 되게.
- 2026-11-16 · SQLite는 URL이 아니라 경로로 연결한다 → 폴더 이름의 공백과 한글이 URL 해석에서 깨지지 않게. 빈 `DATABASE_URL=`이 DB 설정을 통째로 비우던 버그를 이 과정에서 발견해 테스트로 막았다.
- 2026-11-16 · `SECRET_KEY`가 없으면 서버가 아예 뜨지 않게 한다. `DEBUG` 기본값은 False → 설정을 빠뜨린 배포가 디버그 모드로 열리는 사고를 막기 위해.
- 2026-11-16 · Secure 쿠키는 `DEBUG=False`일 때만 켠다 → 개발 서버(http)에서도 로그인이 되게 하면서 배포에서는 강제.
- 2026-11-16 · 모델 이름(`AGENT_MODEL_*`)과 가격표(`MODEL_PRICES`)는 settings에만 둔다 → 모델이 바뀌어도 코드를 고치지 않게. 가격은 공식 가격표를 보고 사람이 채운다.
- 2026-11-16 · 모든 모델이 `TimeStampedModel`을 상속한다 → 생성·수정 시각은 디버깅과 감사 기록의 기본이라서.
- 2026-11-16 · Task / Step / Approval을 세 테이블로 나눈다 → 요청 1건이 도구를 여러 번 부르고(1:N), 그중 외부 행동만 승인이 필요하므로(1:1) 승인 이력을 따로 남긴다.
- 2026-11-16 · Step, Approval, GuardCheck, UsageLog에는 user 외래키를 두지 않는다 → `task.user`로 찾을 수 있고, 같은 값을 두 번 저장하면 어긋날 수 있어서. (개요의 "모든 모델에 user"와 부딪쳐 사용자에게 확인받음)
- 2026-11-16 · `Step.risk_level`은 registry에서 복사해 저장한다 → 나중에 도구 등급이 바뀌어도 당시 기록은 그대로 남게.
- 2026-11-16 · `Message.task`는 SET_NULL, `Memory.source_message`는 CASCADE → 대화 기록은 Task가 지워져도 남기고, 기억은 근거 메시지가 사라지면 함께 지운다.
- 2026-11-16 · Watch 간격 30분 이상을 폼 검증과 DB CheckConstraint 둘 다로 건다 → 도구나 관리자 화면처럼 폼을 거치지 않는 경로에서도 막기 위해.
- 2026-11-16 · Note, Todo 모델은 `tools` 앱에 둔다 → 명세 디렉터리 구조에 따로 자리가 없고, 이 데이터를 다루는 것이 내부 도구뿐이라서.
- 2026-11-16 · Tailwind는 standalone CLI로 빌드하고 결과 CSS(`static/css/app.css`)를 커밋한다 → Node 없이 쓰고, 실행 파일이 없어도 서버는 바로 뜨게. 실행 파일(`bin/`)은 커밋하지 않는다.
- 2026-11-16 · HTMX는 CDN이 아니라 `static/vendor/`에 버전을 고정해 둔다(2.0.4) → 외부 CDN 장애나 변경에 영향받지 않게.
- 2026-11-16 · 화면 높이는 `dvh`, 하단 여백은 `safe-area-inset-bottom` → 모바일 키보드와 아이폰 홈 바에 입력창과 탭이 가려지지 않게.
- 2026-11-16 · `/settings/`는 `/accounts/` 접두사 없이 연결한다 → 명세의 URL 설계를 그대로 따르기 위해.

## 1단계: 에이전트 루프

- 2026-11-16 · 루프는 `LLMClient` 인터페이스만 알고, 실제(`AnthropicClient`)와 가짜(`FakeLLM`)를 끼워 넣는다 → 테스트가 네트워크와 API 요금 없이 돌고, 나중에 다른 모델로 바꿀 여지도 남는다.
- 2026-11-16 · 대화는 LLM을 부를 때마다 DB(Message, Step)에서 다시 조립한다 → 서버 재시작이나 승인 대기 뒤에도 같은 상태에서 이어 가기 위해. 메모리에 들고 있는 대화는 프로세스가 죽으면 사라진다.
- 2026-11-16 · 응답의 thinking 블록은 저장하지도, 다시 보내지도 않는다 → 최신 모델은 다시 보낸 thinking 블록 앞의 대화가 조금이라도 바뀌면 400을 낸다. DB에서 다시 조립하는 구조에서는 "전부 빼고 보내기"가 공식 문서상 허용된 안전한 형태다. 대가로 도구 호출 사이의 추론이 이어지지 않는다.
- 2026-11-16 · Step 하나를 tool_use + tool_result 한 쌍으로 다시 보낸다 → 명세(Step 기록 = 쌍)를 따르고, Step에 "같은 응답" 묶음 정보가 없어서. 병렬 호출도 순서대로 하나씩 보낸 것처럼 보이는 차이가 있다.
- 2026-11-16 · Task는 `UPDATE ... WHERE status='queued'` 한 번으로 잡는다 → 두 곳에서 동시에 실행해도 한쪽만 성공한다. 이미 끝난 Task를 다시 불러도 아무 일도 하지 않는다.
- 2026-11-16 · 상한 검사는 LLM을 부르기 '전에' 한다 → 넘은 뒤에 막으면 이미 돈이 나갔다. 13번째 Step은 시도 자체를 하지 않는다.
- 2026-11-16 · `MODEL_PRICES`가 비어 있으면 실제 API 호출을 막는다 → 가격을 모르면 하루 비용 상한을 계산할 수 없다. 상한이 꺼진 채로 돈이 나가는 상태를 만들지 않는다.
- 2026-11-16 · SDK 자동 재시도(`max_retries`)는 끄고 루프가 2초, 4초로 직접 재시도한다 → 명세의 재시도 규칙을 한 곳에서 지키고, 두 재시도가 겹쳐 대기가 길어지는 것을 막는다. 400처럼 다시 보내도 같은 결과인 오류는 재시도하지 않는다.
- 2026-11-16 · 도구 실행은 `registry.run_tool` 한 곳으로만 하고, EXTERNAL 도구는 여기서 PermissionError를 던진다 → 승인 없는 외부 행동을 프롬프트가 아니라 코드로 막는 첫 단계. 2단계 승인 게이트만 다른 경로로 실행한다.
- 2026-11-16 · 도구가 예외를 던지면 `ok=false`와 일반 문장만 LLM에 준다 → 서버가 죽지 않게 하고, 내부 오류 문구(경로, 개인정보)가 프롬프트로 새지 않게.
- 2026-11-16 · 도구 입력은 jsonschema로 검사하고 `additionalProperties: false`를 건다 → LLM이 만든 입력을 그대로 믿지 않는다. 검사에 실패하면 실행하지 않고 오류를 돌려준다.
- 2026-11-16 · 시스템 프롬프트에는 날짜와 요일만 넣고 분 단위 시각은 넣지 않는다 → 호출마다 프롬프트가 바뀌면 프롬프트 캐시가 깨진다. 도구 목록도 이름순으로 고정한다.
- 2026-11-16 · 메시지 전송은 분당 20회로 제한한다 → 실수나 반복 클릭으로 비용이 튀는 것을 막는다.
- 2026-11-16 · 같은 도구 + 같은 입력의 세 번째 호출은 실행하지 않고 Task를 멈춘다 → 에이전트가 같은 호출을 되풀이하는 루프가 과금 사고의 주범이다. 단계 상한(12)보다 먼저 잡는다. "추가 후 목록 다시 보기"처럼 한 번 다시 부르는 건 정상이라 두 번까지는 허용한다. 입력은 키 순서를 정렬해 비교한다.
- 2026-11-16 · 프롬프트 캐시 표시를 두 곳에 둔다: 시스템 블록 끝(도구 목록 + 시스템 프롬프트, 여러 Task가 공유), 마지막 메시지 끝(같은 Task의 다음 호출이 지금까지의 대화를 다시 읽음) → 에이전트는 같은 앞부분을 반복해서 보내는 구조라 토큰이 가장 많이 새는 곳이다. 표시는 `AnthropicClient`에서만 붙여 루프와 테스트는 그대로 둔다.
- 2026-11-16 · `UsageLog`에 `cache_write_tokens`, `cache_read_tokens`를 추가한다(명세에서 벗어남) → 캐싱을 켜면 API가 캐시 토큰을 `input_tokens`와 따로 보고한다. 빼먹으면 비용이 실제보다 적게 계산되어 하루 비용 상한이 뚫린다. 가격표에도 캐시 쓰기·읽기 가격을 넣고, 하나라도 비면 실제 호출을 막는다.
- 2026-11-16 · Task 토큰 상한에는 캐시에서 읽은 토큰도 포함한다 → 싸게 읽었어도 모델이 실제로 읽은 맥락의 크기이고, 상한의 목적은 대화가 끝없이 커지는 것을 막는 것이라서.
- 2026-11-16 · 비용 절감 중 effort 낮추기와 하루 호출 횟수 제한은 넣지 않는다 → effort는 답변 품질에 영향이 있어 실사용 기록을 보고 정한다. 호출 횟수 제한은 하루 비용 상한과 분당 20회 제한이 이미 같은 역할을 한다.
- 2026-11-16 · 테스트 설정은 .env에 진짜 키가 있어도 모든 외부 API 키를 빈 값으로 덮는다 → 가짜 LLM을 깜빡한 테스트가 실제 과금 호출을 하지 못하게. 이를 확인하는 테스트도 둔다.

## 2단계: 승인 게이트와 감시 에이전트

- 2026-11-16 · 외부 행동의 실행 경로를 `registry.run_external` 하나로 두고, 승인된 Approval이 없으면 예외를 던진다. `run_tool`은 EXTERNAL이면 예외 → 프롬프트로 부탁하면 LLM이 속았을 때 뚫린다. 코드로 막으면 LLM이 무엇을 하든 사람의 승인 없이는 실행 함수에 들어가지 못한다.
- 2026-11-16 · "정확히 한 번 실행"은 Approval을 `select_for_update`로 잠근 뒤 Step을 `waiting_approval -> running`으로 바꾸는 UPDATE 한 번으로 실행권을 얻는 방식으로 지킨다 → 조건부 UPDATE는 동시에 와도 한 요청만 1행을 바꾼다. SQLite에서는 `select_for_update`가 아무 일도 하지 않으므로 이 UPDATE가 실제 방어선이다.
- 2026-11-16 · 외부 호출은 잠금 트랜잭션 밖에서 한다(명세의 "atomic 안에서 실행"과 다름) → 외부 API가 10초 걸리는 동안 DB를 잠그면 SQLite에서 두 번째 클릭이 "database is locked"로 실패한다. 실행권은 이미 잠금 안에서 가져왔으므로 안전성은 같다. 대가로 실행 중 서버가 죽으면 Step이 running으로 남는데, 3단계 워커의 "5분 넘은 running 회수"가 이를 정리한다.
- 2026-11-16 · 실행 가능 조건을 "step이 done이 아님"이 아니라 "step이 waiting_approval임"으로 잡는다 → 실패(failed)한 Step도 다시 실행되지 않게. 명세보다 엄격한 쪽이다.
- 2026-11-16 · 감시 에이전트에는 원래 요청, 도구 이름, 입력, preview 네 가지만 주고 도구는 주지 않는다 → 주입 문장이 숨어 오는 도구 결과를 감시 에이전트는 본 적이 없으므로 같은 방식으로 속지 않는다.
- 2026-11-16 · 감시 에이전트의 어떤 실패(호출 실패, JSON 해석 실패, 예상 못 한 예외)도 `unsure`로 저장하고 작업은 계속한다 → 감시는 경고를 보태는 장치라 장애가 사용자의 일을 막으면 안 된다. 최종 판단은 어차피 사람이 한다.
- 2026-11-16 · 감시 답변은 첫 `{`부터 마지막 `}`까지를 JSON으로 읽는다 → 모델이 JSON 앞뒤에 설명을 붙여도 판정을 살린다.
- 2026-11-16 · 감시 에이전트는 테스트에서 별도 `guard_llm`으로 끼운다(실제 운영에서는 같은 클라이언트) → FAST와 GUARD 기본 모델이 같아 모델 이름으로는 응답을 구분할 수 없다. 응답 순서를 섞지 않고 테스트를 읽기 쉽게.
- 2026-11-16 · EXTERNAL 도구는 preview가 없으면 등록 자체를 막는다 → 사용자가 무엇을 승인하는지 설명할 수 없는 외부 행동은 만들지 않는다.
- 2026-11-16 · 만료 시각이 지난 뒤 누른 승인·거절은 그 자리에서 만료로 처리한다 → 워커의 정리 주기(60초)를 기다리는 사이에 늦은 승인이 실행되지 않게.
- 2026-11-16 · 승인 카드의 버튼은 누르는 즉시 잠근다(화면) + 서버가 두 번째 요청을 무시한다(코드) → 화면 쪽은 사용성, 서버 쪽이 실제 방어다.

## 3단계: 백그라운드 워커와 푸시 알림

- 2026-11-16 · Celery·Redis 없이 DB를 큐로 쓰는 관리 명령(`run_worker`) 하나로 처리한다 → 개인용 규모에 별도 인프라는 과하다. 작업 상태가 전부 DB에 있으므로 웹 서버가 재시작돼도, 화면을 닫아도 작업이 이어진다.
- 2026-11-16 · 메시지 전송, 승인, 거절 요청은 Task를 queued로 바꾸고 바로 응답한다 → 웹 요청이 LLM 응답(수 초~수십 초)을 기다리며 묶이지 않는다. 승인 직후의 외부 호출 한 번만 요청 안에서 하고, 이어지는 LLM 호출은 워커가 한다.
- 2026-11-16 · 워커는 가장 오래된 queued Task를 `select_for_update(skip_locked=True)`로 고르고 조건부 UPDATE로 running으로 바꾼다 → PostgreSQL에서는 워커 여러 개가 서로 기다리지 않고, SQLite에서도 조건부 UPDATE가 "한 Task는 한 번만"을 보장한다.
- 2026-11-16 · 루프는 매 바퀴 `locked_at`을 갱신한다(살아 있다는 신호) → 워커가 "5분 넘게 갱신이 없는 running Task"만 회수하므로, 오래 걸리지만 진행 중인 작업을 실수로 죽이지 않는다.
- 2026-11-16 · 같은 UPDATE로 취소 여부도 확인한다(`status=running`일 때만 갱신) → 사용자가 취소하면 다음 바퀴에서 멈춘다. 끝낼 때도 running일 때만 상태를 바꿔, 늦게 도착한 LLM 답이 취소를 덮어쓰지 않게 한다.
- 2026-11-16 · 승인 후 외부 호출 도중 서버가 죽어 running으로 남은 Step도 5분 뒤 실패로 정리하고, "실제로 반영됐는지 확인하라"고 알린다 → 외부 행동은 반영 여부를 앱이 알 수 없으므로 다시 실행하지 않고 사람에게 확인을 맡긴다.
- 2026-11-16 · 워커는 Task 하나의 예외를 잡아 그 Task만 실패로 닫는다 → 버그 하나로 워커 전체가 멈추지 않게.
- 2026-11-16 · 진행 표시는 HTMX 1초 폴링, 끝나면 `HX-Refresh`로 화면을 한 번 새로 그린다 → 최종 답과 승인 카드를 그리는 곳을 채팅 화면 하나로 유지해 단순하다. SSE로 바꿀 때는 `/tasks/<id>/steps/` 뷰만 바꾸면 된다.
