# 설계 결정 기록

면접 준비용. 결정과 이유를 날짜와 함께 한 줄씩 쌓는다.

## 0단계: 뼈대

- 2026-11-16 · 에이전트 루프를 프레임워크 없이 직접 구현한다 → 승인 게이트와 기록을 루프 안에 코드로 끼워 넣어야 하고, 면접에서 한 줄씩 설명할 수 있어야 해서.
- 2026-11-16 · Django 5.2 LTS로 고정한다(6.x 아님) → 명세가 5.x이고, LTS라 보안 업데이트 기간이 길다.
- 2026-11-16 · DB는 `DATABASE_URL` 하나로 SQLite/PostgreSQL을 바꾼다. 값이 비어 있으면 SQLite → 개발은 설치 없이 바로, 배포는 환경변수만 바꾸면 되게.
- 2026-11-16 · SQLite는 URL이 아니라 경로로 연결한다 → 폴더 이름의 공백과 한글이 URL 해석에서 깨지지 않게. 빈 `DATABASE_URL=`이 DB 설정을 통째로 비우던 버그를 이 과정에서 발견해 테스트로 막았다.
- 2026-11-16 · `SECRET_KEY`가 없으면 서버가 아예 뜨지 않게 한다. `DEBUG` 기본값은 False → 설정을 빠뜨린 배포가 디버그 모드로 열리는 사고를 막기 위해.
- 2026-11-16 · Secure 쿠키는 `DEBUG=False`일 때만 켠다 → 개발 서버(http)에서도 로그인이 되게 하면서 배포에서는 강제.
- 2026-11-16 · 모델 이름(`AGENT_MODEL_*`)과 가격표(`MODEL_PRICES`)는 settings에만 둔다 → 모델이 바뀌어도 코드를 고치지 않게. 가격은 공식 가격표를 보고 사람이 채운다.
- 2026-11-16 · 모든 모델이 `TimeStampedModel`을 상속한다 → 생성·수정 시각은 디버깅과 감사 기록의 기본이라서.
- 2026-11-16 · Task / Step / Approval을 세 테이블로 나눈다 → 요청 1건이 도구를 여러 번 부르고(1:N), 그중 외부 행동만 승인이 필요하므로(1:1) 승인 이력을 따로 남긴다.
- 2026-11-16 · Step, Approval, GuardCheck, UsageLog에는 user 외래키를 두지 않는다 → `task.user`로 찾을 수 있고, 같은 값을 두 번 저장하면 어긋날 수 있어서. (개요의 "모든 모델에 user"와 부딪쳐 사용자에게 확인받음)
- 2026-11-16 · `Step.risk_level`은 registry에서 복사해 저장한다 → 나중에 도구 등급이 바뀌어도 당시 기록은 그대로 남게.
- 2026-11-16 · `Message.task`는 SET_NULL, `Memory.source_message`는 CASCADE → 대화 기록은 Task가 지워져도 남기고, 기억은 근거 메시지가 사라지면 함께 지운다.
- 2026-11-16 · Watch 간격 30분 이상을 폼 검증과 DB CheckConstraint 둘 다로 건다 → 도구나 관리자 화면처럼 폼을 거치지 않는 경로에서도 막기 위해.
- 2026-11-16 · Note, Todo 모델은 `tools` 앱에 둔다 → 명세 디렉터리 구조에 따로 자리가 없고, 이 데이터를 다루는 것이 내부 도구뿐이라서.
- 2026-11-16 · Tailwind는 standalone CLI로 빌드하고 결과 CSS(`static/css/app.css`)를 커밋한다 → Node 없이 쓰고, 실행 파일이 없어도 서버는 바로 뜨게. 실행 파일(`bin/`)은 커밋하지 않는다.
- 2026-11-16 · HTMX는 CDN이 아니라 `static/vendor/`에 버전을 고정해 둔다(2.0.4) → 외부 CDN 장애나 변경에 영향받지 않게.
- 2026-11-16 · 화면 높이는 `dvh`, 하단 여백은 `safe-area-inset-bottom` → 모바일 키보드와 아이폰 홈 바에 입력창과 탭이 가려지지 않게.
- 2026-11-16 · `/settings/`는 `/accounts/` 접두사 없이 연결한다 → 명세의 URL 설계를 그대로 따르기 위해.

## 1단계: 에이전트 루프

- 2026-11-16 · 루프는 `LLMClient` 인터페이스만 알고, 실제(`AnthropicClient`)와 가짜(`FakeLLM`)를 끼워 넣는다 → 테스트가 네트워크와 API 요금 없이 돌고, 나중에 다른 모델로 바꿀 여지도 남는다.
- 2026-11-16 · 대화는 LLM을 부를 때마다 DB(Message, Step)에서 다시 조립한다 → 서버 재시작이나 승인 대기 뒤에도 같은 상태에서 이어 가기 위해. 메모리에 들고 있는 대화는 프로세스가 죽으면 사라진다.
- 2026-11-16 · 응답의 thinking 블록은 저장하지도, 다시 보내지도 않는다 → 최신 모델은 다시 보낸 thinking 블록 앞의 대화가 조금이라도 바뀌면 400을 낸다. DB에서 다시 조립하는 구조에서는 "전부 빼고 보내기"가 공식 문서상 허용된 안전한 형태다. 대가로 도구 호출 사이의 추론이 이어지지 않는다.
- 2026-11-16 · Step 하나를 tool_use + tool_result 한 쌍으로 다시 보낸다 → 명세(Step 기록 = 쌍)를 따르고, Step에 "같은 응답" 묶음 정보가 없어서. 병렬 호출도 순서대로 하나씩 보낸 것처럼 보이는 차이가 있다.
- 2026-11-16 · Task는 `UPDATE ... WHERE status='queued'` 한 번으로 잡는다 → 두 곳에서 동시에 실행해도 한쪽만 성공한다. 이미 끝난 Task를 다시 불러도 아무 일도 하지 않는다.
- 2026-11-16 · 상한 검사는 LLM을 부르기 '전에' 한다 → 넘은 뒤에 막으면 이미 돈이 나갔다. 13번째 Step은 시도 자체를 하지 않는다.
- 2026-11-16 · `MODEL_PRICES`가 비어 있으면 실제 API 호출을 막는다 → 가격을 모르면 하루 비용 상한을 계산할 수 없다. 상한이 꺼진 채로 돈이 나가는 상태를 만들지 않는다.
- 2026-11-16 · SDK 자동 재시도(`max_retries`)는 끄고 루프가 2초, 4초로 직접 재시도한다 → 명세의 재시도 규칙을 한 곳에서 지키고, 두 재시도가 겹쳐 대기가 길어지는 것을 막는다. 400처럼 다시 보내도 같은 결과인 오류는 재시도하지 않는다.
- 2026-11-16 · 도구 실행은 `registry.run_tool` 한 곳으로만 하고, EXTERNAL 도구는 여기서 PermissionError를 던진다 → 승인 없는 외부 행동을 프롬프트가 아니라 코드로 막는 첫 단계. 2단계 승인 게이트만 다른 경로로 실행한다.
- 2026-11-16 · 도구가 예외를 던지면 `ok=false`와 일반 문장만 LLM에 준다 → 서버가 죽지 않게 하고, 내부 오류 문구(경로, 개인정보)가 프롬프트로 새지 않게.
- 2026-11-16 · 도구 입력은 jsonschema로 검사하고 `additionalProperties: false`를 건다 → LLM이 만든 입력을 그대로 믿지 않는다. 검사에 실패하면 실행하지 않고 오류를 돌려준다.
- 2026-11-16 · 시스템 프롬프트에는 날짜와 요일만 넣고 분 단위 시각은 넣지 않는다 → 호출마다 프롬프트가 바뀌면 프롬프트 캐시가 깨진다. 도구 목록도 이름순으로 고정한다.
- 2026-11-16 · 메시지 전송은 분당 20회로 제한한다 → 실수나 반복 클릭으로 비용이 튀는 것을 막는다.
- 2026-11-16 · 같은 도구 + 같은 입력의 세 번째 호출은 실행하지 않고 Task를 멈춘다 → 에이전트가 같은 호출을 되풀이하는 루프가 과금 사고의 주범이다. 단계 상한(12)보다 먼저 잡는다. "추가 후 목록 다시 보기"처럼 한 번 다시 부르는 건 정상이라 두 번까지는 허용한다. 입력은 키 순서를 정렬해 비교한다.
- 2026-11-16 · 프롬프트 캐시 표시를 두 곳에 둔다: 시스템 블록 끝(도구 목록 + 시스템 프롬프트, 여러 Task가 공유), 마지막 메시지 끝(같은 Task의 다음 호출이 지금까지의 대화를 다시 읽음) → 에이전트는 같은 앞부분을 반복해서 보내는 구조라 토큰이 가장 많이 새는 곳이다. 표시는 `AnthropicClient`에서만 붙여 루프와 테스트는 그대로 둔다.
- 2026-11-16 · `UsageLog`에 `cache_write_tokens`, `cache_read_tokens`를 추가한다(명세에서 벗어남) → 캐싱을 켜면 API가 캐시 토큰을 `input_tokens`와 따로 보고한다. 빼먹으면 비용이 실제보다 적게 계산되어 하루 비용 상한이 뚫린다. 가격표에도 캐시 쓰기·읽기 가격을 넣고, 하나라도 비면 실제 호출을 막는다.
- 2026-11-16 · Task 토큰 상한에는 캐시에서 읽은 토큰도 포함한다 → 싸게 읽었어도 모델이 실제로 읽은 맥락의 크기이고, 상한의 목적은 대화가 끝없이 커지는 것을 막는 것이라서.
- 2026-11-16 · 비용 절감 중 effort 낮추기와 하루 호출 횟수 제한은 넣지 않는다 → effort는 답변 품질에 영향이 있어 실사용 기록을 보고 정한다. 호출 횟수 제한은 하루 비용 상한과 분당 20회 제한이 이미 같은 역할을 한다.
- 2026-11-16 · 테스트 설정은 .env에 진짜 키가 있어도 모든 외부 API 키를 빈 값으로 덮는다 → 가짜 LLM을 깜빡한 테스트가 실제 과금 호출을 하지 못하게. 이를 확인하는 테스트도 둔다.

## 2단계: 승인 게이트와 감시 에이전트

- 2026-11-16 · 외부 행동의 실행 경로를 `registry.run_external` 하나로 두고, 승인된 Approval이 없으면 예외를 던진다. `run_tool`은 EXTERNAL이면 예외 → 프롬프트로 부탁하면 LLM이 속았을 때 뚫린다. 코드로 막으면 LLM이 무엇을 하든 사람의 승인 없이는 실행 함수에 들어가지 못한다.
- 2026-11-16 · "정확히 한 번 실행"은 Approval을 `select_for_update`로 잠근 뒤 Step을 `waiting_approval -> running`으로 바꾸는 UPDATE 한 번으로 실행권을 얻는 방식으로 지킨다 → 조건부 UPDATE는 동시에 와도 한 요청만 1행을 바꾼다. SQLite에서는 `select_for_update`가 아무 일도 하지 않으므로 이 UPDATE가 실제 방어선이다.
- 2026-11-16 · 외부 호출은 잠금 트랜잭션 밖에서 한다(명세의 "atomic 안에서 실행"과 다름) → 외부 API가 10초 걸리는 동안 DB를 잠그면 SQLite에서 두 번째 클릭이 "database is locked"로 실패한다. 실행권은 이미 잠금 안에서 가져왔으므로 안전성은 같다. 대가로 실행 중 서버가 죽으면 Step이 running으로 남는데, 3단계 워커의 "5분 넘은 running 회수"가 이를 정리한다.
- 2026-11-16 · 실행 가능 조건을 "step이 done이 아님"이 아니라 "step이 waiting_approval임"으로 잡는다 → 실패(failed)한 Step도 다시 실행되지 않게. 명세보다 엄격한 쪽이다.
- 2026-11-16 · 감시 에이전트에는 원래 요청, 도구 이름, 입력, preview 네 가지만 주고 도구는 주지 않는다 → 주입 문장이 숨어 오는 도구 결과를 감시 에이전트는 본 적이 없으므로 같은 방식으로 속지 않는다.
- 2026-11-16 · 감시 에이전트의 어떤 실패(호출 실패, JSON 해석 실패, 예상 못 한 예외)도 `unsure`로 저장하고 작업은 계속한다 → 감시는 경고를 보태는 장치라 장애가 사용자의 일을 막으면 안 된다. 최종 판단은 어차피 사람이 한다.
- 2026-11-16 · 감시 답변은 첫 `{`부터 마지막 `}`까지를 JSON으로 읽는다 → 모델이 JSON 앞뒤에 설명을 붙여도 판정을 살린다.
- 2026-11-16 · 감시 에이전트는 테스트에서 별도 `guard_llm`으로 끼운다(실제 운영에서는 같은 클라이언트) → FAST와 GUARD 기본 모델이 같아 모델 이름으로는 응답을 구분할 수 없다. 응답 순서를 섞지 않고 테스트를 읽기 쉽게.
- 2026-11-16 · EXTERNAL 도구는 preview가 없으면 등록 자체를 막는다 → 사용자가 무엇을 승인하는지 설명할 수 없는 외부 행동은 만들지 않는다.
- 2026-11-16 · 만료 시각이 지난 뒤 누른 승인·거절은 그 자리에서 만료로 처리한다 → 워커의 정리 주기(60초)를 기다리는 사이에 늦은 승인이 실행되지 않게.
- 2026-11-16 · 승인 카드의 버튼은 누르는 즉시 잠근다(화면) + 서버가 두 번째 요청을 무시한다(코드) → 화면 쪽은 사용성, 서버 쪽이 실제 방어다.

## 3단계: 백그라운드 워커와 푸시 알림

- 2026-11-16 · Celery·Redis 없이 DB를 큐로 쓰는 관리 명령(`run_worker`) 하나로 처리한다 → 개인용 규모에 별도 인프라는 과하다. 작업 상태가 전부 DB에 있으므로 웹 서버가 재시작돼도, 화면을 닫아도 작업이 이어진다.
- 2026-11-16 · 메시지 전송, 승인, 거절 요청은 Task를 queued로 바꾸고 바로 응답한다 → 웹 요청이 LLM 응답(수 초~수십 초)을 기다리며 묶이지 않는다. 승인 직후의 외부 호출 한 번만 요청 안에서 하고, 이어지는 LLM 호출은 워커가 한다.
- 2026-11-16 · 워커는 가장 오래된 queued Task를 `select_for_update(skip_locked=True)`로 고르고 조건부 UPDATE로 running으로 바꾼다 → PostgreSQL에서는 워커 여러 개가 서로 기다리지 않고, SQLite에서도 조건부 UPDATE가 "한 Task는 한 번만"을 보장한다.
- 2026-11-16 · 루프는 매 바퀴 `locked_at`을 갱신한다(살아 있다는 신호) → 워커가 "5분 넘게 갱신이 없는 running Task"만 회수하므로, 오래 걸리지만 진행 중인 작업을 실수로 죽이지 않는다.
- 2026-11-16 · 같은 UPDATE로 취소 여부도 확인한다(`status=running`일 때만 갱신) → 사용자가 취소하면 다음 바퀴에서 멈춘다. 끝낼 때도 running일 때만 상태를 바꿔, 늦게 도착한 LLM 답이 취소를 덮어쓰지 않게 한다.
- 2026-11-16 · 승인 후 외부 호출 도중 서버가 죽어 running으로 남은 Step도 5분 뒤 실패로 정리하고, "실제로 반영됐는지 확인하라"고 알린다 → 외부 행동은 반영 여부를 앱이 알 수 없으므로 다시 실행하지 않고 사람에게 확인을 맡긴다.
- 2026-11-16 · 워커는 Task 하나의 예외를 잡아 그 Task만 실패로 닫는다 → 버그 하나로 워커 전체가 멈추지 않게.
- 2026-11-16 · 진행 표시는 HTMX 1초 폴링, 끝나면 `HX-Refresh`로 화면을 한 번 새로 그린다 → 최종 답과 승인 카드를 그리는 곳을 채팅 화면 하나로 유지해 단순하다. SSE로 바꿀 때는 `/tasks/<id>/steps/` 뷰만 바꾸면 된다.
- 2026-11-16 · 푸시 공개 함수는 `notify(user, kind, url)`이고 제목·본문은 kind별 고정 문구다(3단계 후속 프롬프트의 title, body 인자를 쓰지 않음) → 호출하는 쪽이 개인 내용을 넣을 방법 자체를 없애, "푸시에 개인 정보 금지"를 함수 모양으로 강제한다. 푸시는 구글·애플 서버를 거친다.
- 2026-11-16 · 완료 푸시는 시작 후 20초가 넘었거나 자동 작업일 때만, 실패 푸시(한도 초과 포함)는 항상 보낸다 → 짧은 채팅 답은 화면에서 바로 보이므로 알림이 소음이 된다.
- 2026-11-16 · 푸시 실패는 로그만 남기고 작업을 실패시키지 않는다. 404/410이면 구독을 지운다 → 알림은 부가 기능이다. 로그에는 구독 id만 남기고 내용과 키는 남기지 않는다.
- 2026-11-16 · 서비스 워커는 `/static/sw.js`가 아니라 `/sw.js`로 내보낸다 → 서비스 워커는 자기 경로 아래만 맡을 수 있어서, 사이트 전체의 알림 클릭을 처리하려면 루트에 있어야 한다. 알림을 누르면 이 사이트 안의 주소만 연다.
- 2026-11-16 · VAPID 키는 관리 명령으로 만들어 `.env`에 바로 쓴다(화면에 출력하지 않음) → 개인키가 터미널 기록이나 대화 기록에 남지 않게. 공개키만 설정 화면에 넣는다.
- 2026-11-16 · 알림 설정 화면은 서비스 워커 확인에 5초 제한을 두고, 실패하면 이유를 보여 준다 → 서비스 워커가 막힌 브라우저에서 화면이 아무 반응 없이 멈춘 것처럼 보이던 문제를 점검 중에 발견했다.

## 4단계: 실제 도구

- 2026-11-16 · 외부 HTTP는 `tools/http.get_json` 한 곳으로만 보낸다(타임아웃 10초, 재시도 1회) → 재시도·오류 문장·키 숨기기를 도구마다 따로 만들면 하나쯤 빠진다. 재시도는 타임아웃·연결 실패·5xx만 하고, 4xx는 다시 보내도 같아서 하지 않는다.
- 2026-11-16 · 카카오 한도 초과는 HTTP 429가 아니라 400 + code -10이라 따로 잡는다 → 공식 에러 코드 문서에서 확인. 명세의 "429 테스트"만 믿었으면 한도 초과를 일반 요청 오류로 잘못 안내했을 것이다.
- 2026-11-16 · 외부 API 오류 문장에는 응답 본문과 요청 헤더를 넣지 않는다 → 이 문장은 LLM과 화면에 그대로 간다. 키가 섞이지 않는 것을 테스트로 확인한다.
- 2026-11-16 · 날씨는 Open-Meteo(키 없음) + 카카오 키워드 검색(좌표 변환) → 카카오 키 하나로 날씨의 좌표 변환과 장소 검색을 함께 해결한다. 네이버 지역 검색은 결과 5개 제한과 반경 검색이 없어서, Google Places는 결제 카드가 필요해서 고르지 않았다.
- 2026-11-16 · 카카오 키워드 검색은 '성수동'에 '서울숲카페거리'처럼 그 동네의 장소를 돌려준다. 결과의 place에는 사용자가 말한 이름을 두고, 실제로 좌표를 잡은 장소는 matched_place로 따로 남긴다 → 좌표는 맞지만 이름이 바뀌면 사용자가 헷갈린다. 실제 응답을 저장해 보고 발견했다.
- 2026-11-16 · 날짜는 서울 기준 오늘~15일 뒤만 받고, 그 밖이거나 형식이 틀리면 API를 부르지 않는다 → Open-Meteo 예보는 16일까지다. 쓸모없는 호출을 줄이고 이유를 바로 알려 준다.
- 2026-11-16 · 날씨 결과의 출처에 Open-Meteo를 항상 넣는다 → 무료 API가 CC-BY 4.0이라 출처 표기가 조건이다.
- 2026-11-16 · 시간대별 예보는 3시간 간격 8개로 줄여 LLM에 보낸다 → 24개를 다 보내면 이후 모든 호출에 따라붙는 토큰이 세 배가 된다.
- 2026-11-16 · search_places 결과는 이름, 주소, 카테고리, 전화, 링크, 좌표, 거리만 남긴다 → 카카오 원본의 id, 카테고리 코드 등은 답변에 쓰이지 않는데 이후 모든 호출의 토큰으로 따라붙는다.
- 2026-11-16 · 빈 전화번호는 None, 거리 문자열은 정수(좌표 없이 검색하면 None)로 바꾼다 → 실제 응답을 저장해 보니 전화번호가 빈 문자열인 가게가 있고, distance가 문자열이며 좌표가 없으면 빈 문자열이었다.
- 2026-11-16 · 도구 설명에 "영업시간과 가격은 결과에 없으니 말하지 않는다"를 넣는다 → 실제 호출에서 "영업시간도 알려줘"에 모델이 "확인되지 않았다"고 답하는 것을 확인했다. 피클의 '틀린 주소·가격' 사례를 막는 장치다.
- 2026-11-16 · 네이버 검색은 개발자센터가 아니라 NAVER API HUB(네이버클라우드)를 쓴다 → 2026-07-31부터 개발자센터의 검색 API 신규 신청이 막혔다. 주소(`naverapihub.apigw.ntruss.com/search/v1/webkr`)와 헤더(`X-NCP-APIGW-API-KEY-ID/KEY`)가 바뀌었고 요청·응답 모양은 같다. 키 발급 과정에서 이 변경을 처음 알았다.
- 2026-11-16 · 실패 응답은 실제로 받아 저장한 뒤 테스트한다 → 네이버는 401 본문의 errorCode가 "200"이고, 파라미터 오류는 다른 모양({errorCode: "SE02"})이다. 본문 코드를 믿지 않고 HTTP 상태로 판단하는 공통 호출이 이 차이를 흡수한다.
- 2026-11-16 · 웹 검색 결과에서 `<b>` 태그를 지우고 HTML 엔티티를 되돌린다. 결과는 최대 10개만 LLM에 넘긴다 → API는 100개까지 주지만 이후 모든 호출에 따라붙는다.
- 2026-11-16 · web_search는 external_content=True → 남이 쓴 웹 글 속 지시문을 명령으로 받지 않게 경고문으로 감싼다(절대 원칙 7).
- 2026-11-16 · 21일 지난 웹 검색 결과는 워커가 Step 기록에서 지운다(성공 여부와 입력은 남김) → 네이버 API 이용약관 7.3조가 허용 범위를 넘는 저장(캐시 포함)을 금지한다. 검색 API 특약의 정확한 보관 기간은 공식 문서로 확인하지 못했고, 기사에 나온 21일을 넘지 않게 잡았다. 특약을 확인하면 `SEARCH_RESULT_RETENTION`만 바꾸면 된다.
- 2026-11-16 · 읽기(GET)만 1회 재시도하고 쓰기(POST, PATCH, DELETE)는 재시도하지 않는다(명세의 "재시도 1회"를 읽기에만 적용) → 일정 생성 요청이 타임아웃 나도 구글에는 이미 만들어졌을 수 있다. 다시 보내면 같은 일정이 두 번 생긴다.
- 2026-11-16 · Google OAuth는 명세대로 google-auth-oauthlib(Flow)로 하고, Calendar 호출과 토큰 갱신은 google-api-python-client 대신 tools/http로 REST를 직접 부른다(사용자 확인) → 타임아웃·재시도·한국어 오류·키 숨기기를 다른 외부 도구와 같은 한 곳에서 지키고, 실제 응답 fixture로 테스트한다. httplib2 등 의존성도 줄어든다.
- 2026-11-16 · OAuth 시작 때 state와 PKCE code_verifier를 세션에 함께 저장하고, 콜백에서 state가 다르면 아무것도 저장하지 않는다(400) → state는 CSRF 방어. google-auth-oauthlib가 code_verifier를 자동으로 만드는데 공식 문서에는 없어서 라이브러리 코드를 읽고 알았다. 빠뜨리면 토큰 교환이 실패한다.
- 2026-11-16 · 토큰 교환은 `fetch_token(code=...)`로 한다 → 콜백 URL 전체를 넘기는 방식은 http localhost에서 oauthlib의 https 검사(`OAUTHLIB_INSECURE_TRANSPORT`)를 꺼야 한다. 코드만 넘기면 그 설정 없이도 된다.
- 2026-11-16 · 토큰(access, refresh, 만료 시각)은 JSON 통째로 Fernet 암호화해 저장하고, 범위(scopes)만 평문 칸에 둔다 → 권한 확인(메일 읽기 권한이 있는가)은 복호화 없이 하고, 토큰 자체는 DB가 유출돼도 키 없이는 못 읽는다.
- 2026-11-16 · refresh token 갱신이 400/401(invalid_grant)이면 "다시 연결" 안내로 바꾼다 → 외부 사용자 유형 + 테스트 상태 앱은 refresh token이 7일 뒤 만료된다(구글 공식 문서). 개인 프로젝트는 테스트 상태로 쓰므로 주마다 겪는 일이다.
- 2026-11-16 · 연결 해제는 구글 쪽 권한 철회(revoke)를 시도하되, 실패해도 우리 쪽 토큰은 지운다 → 이미 만료된 토큰은 철회가 실패한다. 우리 DB에서 지우는 것이 더 중요하다.
- 2026-11-16 · Calendar 도구 입력 시각은 서울 기준 'YYYY-MM-DDTHH:MM'(스키마 pattern으로 검사)이고, 보낼 때 timeZone=Asia/Seoul을 붙인다 → LLM이 UTC 오프셋을 계산하다 틀리는 일을 없앤다. 끝이 시작보다 빠르면 승인 요청 전에 막는다.
- 2026-11-16 · list_events에서 일정이 없는 것은 ok=true + 빈 목록이다(명세의 "빈 결과 ok=false"를 이 도구에는 적용하지 않음) → "그날은 일정이 없습니다"는 실패가 아니라 정답이다. 실패로 돌려주면 에이전트가 사과하거나 재시도한다.
- 2026-11-16 · 지운 일정을 조회하면 404가 아니라 200 + status 'cancelled'가 온다(실제 응답으로 확인). 이 경우 '찾지 못함'으로 처리한다 → 그대로 두면 이미 지운 일정에 '삭제합니다' 승인 카드가 정상처럼 뜬다. 다시 삭제하면 410이 온다.
- 2026-11-16 · 수정 preview는 바꾸기 전 일정을 조회해 '전 → 후'를 보여 주고, 삭제 preview는 지워질 일정의 제목과 시각을 조회해 보여 준다 → 사용자가 event_id가 아니라 실제 내용을 보고 승인한다. 엉뚱한 일정을 지우는 실수를 사람이 잡을 수 있다.
- 2026-11-16 · Calendar 실제 응답은 사용자 허락을 받아 2027년 1월에 테스트 일정을 만들고 고치고 지워서 얻었고, 이메일 주소는 모두 지우고 그날의 다른 일정은 걸러서 저장했다 → 테스트 자료가 깃에 올라가도 개인 정보가 남지 않게.
- 2026-11-16 · 시스템 프롬프트에 "외부 행동은 승인 카드가 확인하니 채팅으로 따로 승인을 묻지 말고 바로 도구를 호출하라(빠진 정보는 합리적 기본값, 약속은 2시간)"를 추가한다(명세 문구에 한 줄 추가, 사용자 확인) → 실사용에서 모델이 "승인해 주시면 등록하겠습니다"라고 먼저 물어, 사용자가 채팅 "승인" + 승인 카드로 두 번 확인했다.

## 화면 디자인 (frontend-design 스킬)

- 2026-11-16 · 디자인 컨셉은 "결재"다. 승인 카드는 결재란(요청/승인)이 있는 결재 서류로, 승인을 거쳐 실행된 외부 행동에는 붉은 "승인" 인장을 찍는다 → 이 앱의 정체성은 "내가 승인해야만 밖으로 나가는 비서"이고, 한국 사용자에게 가장 익숙한 승인의 모양이 결재와 도장이다. 대담함은 이 두 곳에만 쓰고 나머지는 조용하게 둔다.
- 2026-11-16 · 첫 안(따뜻한 크림 배경 + 명조)은 생성형 디자인의 흔한 기본값이라 버리고, 차가운 회청색 종이(#EEF1F4) + 남색 먹(#1D2733) + 인주(#B8322A, 인장에만)로 바꿨다.
- 2026-11-16 · 글꼴은 제목 Hahmlet(명조), 본문 IBM Plex Sans KR. 한국 웹 기본값인 Pretendard는 일부러 피했다. 한국어 줄바꿈은 word-break: keep-all.
- 2026-11-16 · 에이전트 답은 말풍선 대신 왼쪽 선(기록처럼), 단계는 실제 순서라 세로선 타임라인, 설정·작업 기록은 같은 카드 반복 대신 한 장의 지면 + 구분선, 하단 탭은 이모지 대신 같은 굵기의 선 아이콘.
- 2026-11-16 · 다크 모드는 CSS 변수만 바꾼다(템플릿에 dark: 클래스를 반복하지 않음) → 색을 한 곳에서 관리하고, 새 화면이 다크 모드를 빠뜨리지 않는다.
- 2026-11-16 · 움직임은 승인 직후 인장이 찍히는 순간 하나만(30초 이내 승인된 것), prefers-reduced-motion이면 끈다.

## 5단계: 기억

- 2026-11-16 · remember는 서버가 세 가지를 검사한다: 채팅으로 시작한 Task인가, 이 Task에서 외부 내용 도구(웹 검색·일정 조회·메일)를 아직 안 썼는가, 저장할 내용의 핵심 단어가 시작 메시지에 실제로 있는가 → 피클이 메일·프로필을 종합해 말한 적 없는 자녀 정보를 알아낸 사례를 프롬프트가 아니라 코드로 막는다.
- 2026-11-16 · "핵심 단어가 있는가"는 형태소 분석기 없이, 조사·어미를 떼어 낸 2글자 이상 단어의 60% 이상이 메시지에 있으면 통과로 정했다(명세에 기준이 없어 직접 정함) → 의존성 없이 설명 가능한 규칙. "라떼를 좋아해, 기억해" → "라떼를 좋아함"은 통과, "서울에 산다" 같은 추측은 거부.
- 2026-11-16 · 도구가 실행 중인 Task를 알아야 할 때를 위해 Tool에 needs_task 옵션을 둔다 → remember만 Task(출처 메시지, origin, 이전 Step)를 받는다. 다른 도구의 시그니처는 그대로.
- 2026-11-16 · 프롬프트에는 기억을 최근 30줄만 넣고, 이번 Task에서 저장한 기억은 빼서 다음 Task부터 보이게 한다 → 같은 Task 안에서 시스템 프롬프트가 바뀌면 프롬프트 캐시가 깨진다. 시각 비교는 '같거나 이전'으로 하고 이번 Task 기억은 출처로 뺀다(Windows 시계 해상도 때문에 같은 시각이 찍혀 테스트가 흔들린 것을 고침).
- 2026-11-16 · 기억 삭제는 is_active=False가 아니라 행 삭제(명세) → "지웠다"가 정말 지운 것이어야 한다.
- 2026-11-16 · 기억 화면은 각 기억 아래에 근거가 된 사용자 말을 「 」로 인용한다(frontend-design) → "왜 이걸 기억하지?"를 바로 확인하고 지울 수 있게. 출처가 보이는 것이 이 기능의 신뢰를 만든다.

## 6단계: 예약 작업, 조건 감시, 아침 브리핑

- 2026-11-16 · 예약 작업은 실행 시각에 origin=schedule Task를 큐에 넣기만 하고, 실행은 일반 워커 경로가 한다 → 루프가 READ 도구만 넘기고 승인 요청도 막으므로(테스트 5, 14) 자동 작업 전용 실행 코드를 따로 만들 필요가 없다.
- 2026-11-16 · 조건 감시는 Task를 만들지 않는다. 저장된 READ 도구를 직접 실행하고 FAST 모델이 {met, summary}만 판단한다(도구는 주지 않음) → 감시 경로에는 행동할 방법 자체가 없다. 판단 비용은 UsageLog(purpose=watch)로 남기고 하루 비용 상한에 닿으면 감시도 쉰다.
- 2026-11-16 · 감시 도구 제한은 서버에서: READ만, 외부 글 도구는 web_search만(list_events 거부), 메일 도구 이름 금지, 도구 입력은 그 도구의 스키마로 검사, 간격 30분 이상(폼·도구·DB 제약 세 겹), 활성 10개, 기본 만료 30일.
- 2026-11-16 · 예약 작업과 감시의 '이번 회차'는 next_run_at을 다음 값으로 바꾸는 조건부 UPDATE 한 번으로 잡는다 → 워커가 둘이어도 한 회차는 한 번만 실행된다(Task 실행권과 같은 방식).
- 2026-11-16 · 예약 작업은 시각 하나 + 요일 목록 구조라 하루에 두 번 이상 돌 수 없다 → 명세의 "하루 1회보다 잦을 수 없음"을 별도 검사가 아니라 데이터 구조로 보장한다.
- 2026-11-16 · 아침 브리핑은 새 계정 생성 신호(post_save)로 만들고, 이미 있는 계정은 데이터 마이그레이션으로 채운다. 설정 화면에서 시각과 켜기/끄기를 바꾸면 다음 실행 시각을 다시 계산한다.
- 2026-11-16 · 제안 형식("[제안] "으로 시작하는 한 줄 요청)을 시스템 프롬프트에 명시한다(명세의 요구를 모델에게 알려 주는 것) → 실사용에서 형식을 안 알려 주니 모델이 '💡 제안' 목록으로 써서 버튼이 되지 않았다. 모델이 습관적으로 붙이는 '제안' 소제목 줄은 화면에서 지운다.
- 2026-11-16 · 모델 답변의 **굵게**를 굵은 글씨로 보여 주되, HTML을 먼저 전부 이스케이프한 뒤 바꾼다 → 답변이나 도구 결과에 섞인 태그가 실행되지 않는다. 1단계부터 별표가 그대로 보이던 문제를 브리핑에서 발견해 고쳤다.
- 2026-11-16 · 자동화 화면은 '시각표'(frontend-design): 예약 작업 왼쪽에 실행 시각을 명조 숫자로 크게, 조건 감시는 시각 대신 조건 문장을 인용으로 앞에 둔다. 켜기/끄기는 role=switch 스위치.

- 2026-11-16 · 이전 Task의 도구 기록 요약을 다음 사용자 메시지 앞 "[앱 기록]"으로 모델에 보낸다(DB는 그대로) → 모델이 앞서 한 일을 몰라 같은 감시를 다시 만든 버그 수정. 사용자 차례에 붙여 형식 흉내와 캐시 깨짐을 피하고, 외부 글은 옮기지 않는다.
- 2026-11-16 · 같은 조회의 감시, 같은 시각·요일·내용의 예약 작업은 서버가 거절한다 → 프롬프트(부탁)만 믿지 않고 코드로 한 번 더 막는다. 같은 조회에 다른 조건을 걸고 싶으면 기존 감시를 지우고 다시 만든다(개인용이라 드문 경우).

## 7단계: 음성 입력, 메일 읽기, 답장 초안

- 2026-11-16 · 음성 입력은 브라우저 SpeechRecognition(ko-KR)만 쓴다. 인식한 글자는 입력창에만 채우고 전송은 사용자가 누른다. 미지원 브라우저는 버튼을 숨긴 채 둔다. 음성은 서버로 가지 않는다.
- 2026-11-16 · gmail.readonly는 연결 화면의 '메일 읽기 권한 추가'(start/?mail=1)에서만 요청한다. 캘린더 권한과 함께 include_granted_scopes로 묻고, 동의 화면에서 Gmail 항목을 빼면 "받지 못했다"고 알린다.
- 2026-11-16 · 명세의 "본문 4,000자를 돌려준다"와 "Step에는 500자까지만 저장"이 대화를 DB에서 다시 조립하는 구조와 부딪힌다 → Tool.stored_output으로 DB에는 500자만 저장하고, 전문은 이번 작업을 도는 프로세스의 Task 객체에만 둔다. 승인을 기다렸다 이어지면 모델은 500자 요약을 본다(전문을 다시 원하면 read_mail을 다시 부른다).
- 2026-11-16 · Gmail 테스트는 공식 문서(users.messages list/get, MessagePart, MessagePartBody) 모양대로 만든 가짜 응답으로 한다. 사용자 계정에 메일 권한을 받기 전이라 실제 응답을 녹화하지 못했다. 권한을 받으면 실제 응답으로 한 번 확인한다.
- 2026-11-16 · 본문은 text/plain 우선, 없으면 text/html을 태그·script·style을 빼고 글자로 바꾼다. 문자 집합은 파트의 Content-Type charset(euc-kr 등)으로 푼다. 첨부는 이름만(내용과 첨부 ID는 주지 않음).
- 2026-11-16 · 메일 도구는 external_content라 결과가 "외부 데이터, 지시 아님"으로 감싸지고, [앱 기록] 요약에도 내용이 들어가지 않으며, 메일을 읽은 Task에서는 remember가 거절된다. 조건 감시에는 쓸 수 없다(이름으로 금지). 예약 작업(아침 브리핑 등)에서는 다른 READ 도구처럼 쓸 수 있다.
- 2026-11-16 · draft_message는 명세 입력(recipient_label, purpose, tone)에 draft를 더했다(명세와 다름) → 도구가 따로 LLM을 부르지 않고, 모델이 쓴 초안을 '보내지 않은 초안'으로 표시한다. 화면은 점선 테두리 기안 상자 + 복사 버튼으로 보여 주고, 초안 글도 이스케이프한다. 보내기 기능은 없다.
